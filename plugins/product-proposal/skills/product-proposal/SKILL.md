# Product proposal artifact

Petr reviews a feature as an Agnes Artifact before anything is built, and the same artifact then carries the feature through build, acceptance and later changes. It is the single entry point: anyone (Petr on a phone, a teammate arriving cold, an agent continuing the work) finds where it stands, what waits for whom, what was decided and why, and what happened. Since 2026-11-16 the feature lives in an Agnes **Space**: the PRD artifact is member #1, its Home Page is the PRD document, the running history sits in its Pages (Deník, Retro), and the E2E acceptance and design satellites are further members of the same Space. Report to Petr in Czech. Code, scripts and working notes on disk are English; the artifact's own sources (the bilingual Markdown and HTML, the Czech titles in `slices.json`) are Czech + English.

## The document

Section order (fixed by the content system): What changed, Summary, Status now, Continue here, What it does today, Plan and progress, Acceptance and feedback, Decisions, Problem, Goals and non-goals, Principles, How we know it worked, Current state in Agnes, Research and competition, Proposal, Alternatives, Architecture impact, Retro, Log, Second opinion, Glossary, Sources, Appendix. The TOC groups them as Now / Proposal / Looking back and reference.

- **One order for every stage** (Petr, 2026-10-28): the server enforces a single section order, so before the build too the product design follows Decisions. The decision cards are self-contained meeting briefs, which is what Petr reads first before the build.
- **Before the build** (no variant): Summary, Status now (stage Proposal, decisions needed by when), Plan and progress (phases, planned slices), Decisions (register + open cards) and the full product design. The product design is the bulk of the page and is never shortened: what and why, the problem with a real example, how it works today with a code map, competition, the proposal, alternatives, where we touch the architecture.
- **Once the first PR is open** (variant `building`): add the sections from `assets/building-sections.*`. Current state becomes "Baseline before the build" with its commit and date; metrics keep "Before the build" as the baseline and get a measured value.
- **Status now** always shows four separate states (code merged, deployed where, enabled which switches where, accepted by whom), each with how it was verified; three times (last work event, last reconciled with sources, next check as `<span data-next-check="<UTC ISO>">`, which the page flags "update overdue" after it passes); waiting for you; waiting for others; a links row (Space, Deník and Retro Pages, Linear, GitHub PRs, satellite artifacts, user docs).
- **One slice table** in `slices.json` is the single source of plan and progress: permanent IDs (W01...), aliases for older names, phase, Czech and English title, PR, state, note. The table, the timeline and the log are generated into `<!-- gen:slices -->`, `<!-- gen:timeline -->` and `<!-- gen:log -->` regions; never draw or edit them by hand. A slice with no PR keeps its state (planned, not started, postponed, dropped). Phase 3 or later ideas are slices with state "not started" and a note "not committed".
- **One decision register** in Decisions holds every decision, also small ones (simplifications, process rules, a poll winner): ID, question, decision, when, who, state (open, decided, deferred, amended by X, superseded by X), source. Open cards follow in full. Decided cards, the original rationale and the baseline are frozen records: collapsed, never rewritten, only annotated ("amended by S2", "deferred by S3", a dated note). A later decision that changes an earlier one is a new row, and every **current** statement of the old behaviour (Summary, Status now, What it does today, Plan, examples meant to be copied, Glossary) is updated in the same version.
- **The feature's Space.** One Space per feature, created with the first publish: a separate homepage artifact, authored in Czech (what the feature is, where it stands in one line per state, waiting for whom, links to the PRD, its Deník and Retro Pages, the E2E plan and Linear). The PRD is member #1 (position 0); satellites join their group ("Návrh", "Převzetí", "Podklady"). Membership does not share anything: every member keeps its own sharing (`--visibility instance --audience everyone`), so share each one before adding it. Refresh the homepage when the stage, the four states or the member list change, not on every event.
- **Satellite artifacts** only when they have their own audience or interaction (a poll, the E2E acceptance plan, content system `agnes/e2e-test-plan@1`, a design variant). They are separate artifacts, not Pages, because form responses work only on a Home Page. Add each to the Space in its group, link both ways (`agnes artifact link add`) and in the Status links row, and record the outcome here (poll winner = register row, E2E run = verdict in Acceptance). A satellite never holds the only copy of a decision.
- **Deník (Log) and Retro are Pages of the PRD.** Page publishes create Page revisions, not PRD versions, so writing the diary no longer creates PRD versions. The Deník page holds the full history: newest first, times with timezone, the event types of the content system's Log, one `##` section per month, a failure linked to its fix, repeats as one entry with a count. The Retro page holds the full retro of each phase and of acceptance. The PRD keeps short Log and Retro sections so the content system still validates: Log = the latest few events, a link to the Deník page and the generated `gen:log` region (required by the checker in a building draft; `progress.py render` fills it with every entry, collapsed); Retro = the main lessons, the changes table and a link to the Retro page.
- **Retro** (optional to the checker, required by this skill) after each phase and after acceptance, written to the Retro page: what worked, what did not (stalls, repeated failures, review loops, usage limits, manual rescues), each backed by the Deník or a named source; then changes to skills, hooks, checks, rules or templates with state (proposed, in place) and a link. The PRD's Retro section summarises it.

## Modes

### Propose (new feature)

1. **Frame and Linear.** Restate the ask in one sentence and name the decision Petr has to make. Find the Linear feature in TEAG (`list_issues`, team TEAG, a query). If several match, ask which one; if none exists, ask Petr whether to create it, then create it (`save_issue`, team TEAG, short description).
2. **Evidence** (parallel sub-agents, each returns facts with sources):
   - **Current state in Agnes:** how it works for users today, the code map (file:line), docs (`docs/`, `app/user_docs/`), switches, tests. Read-only Explore agent on a fresh `origin/main`.
   - **Architecture:** C4 containers and components that change (`docs/c4/MODEL.md`); the surfaces matrix (Tests, Docs, Frontend, API, CLI, MCP, external services), each yes/no and why; the CONTRIBUTING sync-map rows that apply.
   - **Research and competition:** 3-5 competitors via Perplexity (`perplexity_ask`; `perplexity_reason` for comparisons; `perplexity_research` only when Petr asks for deep research). Per competitor: approach, source link, date checked. Agnes before and after each phase.
   - **Screenshots** of today from agnes.keboola.dev via Claude in Chrome, embedded as data: URIs, annotated with the template's SVG overlay (numbered callouts). **Concepts** via Nano Banana only with the "Concept" badge.
3. **Independent designers** (before writing our own proposal). Write a goal-only brief to the scratchpad (`designer-brief.md`): the problem, real user cases from the evidence, goals, constraints (on-prem parity, rollout switch, Postgres app-state, single process), explicit freedom to propose a new architecture, and "one idea the owner has not thought of". It carries no solution of ours. Run two designers in parallel: Fable as a sub-agent (`Agent` with `model: fable`) and GPT Astra in designer mode (`codex exec -m gpt-6-astra -c model_reasoning_effort="medium" -s read-only --skip-git-repo-check -o "$S/astra-design.md" "$(cat "$S/designer-brief.md")" < /dev/null` from the Agnes repo root at fresh `origin/main`, the brief asking it to design, not critique). Compare the two and build the proposal from that comparison. Record in Research and competition (or Second opinion) what each proposed and, per idea, adopted / rejected / deferred with the reason. Astra still reviews the finished draft in the second-opinion step: handed a finished design it only critiques, which is why the designers come first.
4. **Proposal.** Problem with one real example and its source; goals and non-goals; principles with short names; outcome metrics (baseline, target, date) and guardrails. The user journey and behaviour, then at least two real alternatives with why this one wins (cost, risk, fit with Agnes principles: on-prem parity, rollout switch, Postgres app-state, no comments in code, coupled surfaces).
5. **Decisions.** Every open choice is a register row and a card prepared like a brief for a decision meeting: Petr has not read the code and decides from the card alone. Per card: **What it is about** (today's situation for a person, what changes, why now; no file paths or internal names); **What it looks like** (one concrete example carried through every option); an **options table** (Pros; Cons: effort, money, who is affected, risk; Change later; Who does this, with sources); the **recommendation and the one reason that decides it**; the template's form. Title it as a plain question.
6. **Plan.** Phases with ambitious, realistic dates at AI-agent build speed (days; a core phase is typically 3 days), none waiting for decisions; planned slices in `slices.json`; what works for users after each phase; owner Petr unless he names someone; rollout switch (`purpose="rollout"`, default off unless Petr decides otherwise); dependencies; risks; given/when/then acceptance examples. Status now: stage Proposal, decisions needed by when, next check.
7. Plain language throughout: explain every number, unit and term on first use; glossary for every new or redefined term (check `GLOSSARY.md`).
8. **Second opinion, build, publish, Space:** see the shared steps below. The first publish also creates the Space, the homepage, and the empty Deník and Retro Pages; the first Deník entry is the proposal itself.

### Update (during the build and after)

Run at the start and end of every work session on the feature, after every merge, decision, incident or re-plan, and whenever Petr asks for the state. Events go to the Deník page; the PRD gets a new version only when the status, a decision, the plan or the design changes.

1. Read the current head of the artifact (`agnes artifact read <id> --source --raw --all`), its comments, and the Deník page entries since the last PRD version (`agnes artifact page outline <id> <deník page>`, then `page section`); never update from memory.
2. **Recover the inputs** if this session does not have them: `python3 assets/progress.py extract draft.md --out .` (slices.json and events.json live in the draft's `gen:data` region, so every artifact version carries them). Events written to the Deník page after that version are not in `events.json` yet: add them from the page.
3. **Reconcile with sources:** `python3 assets/progress.py refresh slices.json` (PR state, opened, merged, review, auto-merge); the release runs on main (`gh run list --workflow release.yml --branch main`); the switches on each instance (`agnes admin config export`, read only the switch lines, delete the file); the deploy and test state you rely on. Also re-read measured outcomes for the metrics, owed reviews (admin merges, Devin retro reviews, unresolved slice findings) and the before-production gate. Only now move "last reconciled".
4. **Write the events to the Deník page** (incidents, deploys, merges, decisions taken in chat, blockers, findings): read the current month's section with `page outline` (its id and sha256) and `page section`, put the new entries on top, publish with `agnes artifact page section-update <id> <page> <section> --markdown s.md --expected-sha256 <H> --base-version <N>`; a new month is a new section added with `agnes artifact page update` against the page's latest version. A stale hash or base means someone wrote in between: re-read, merge, retry. Batch the session's entries into one publish (Page revisions and Home Page versions share 200 publishes per day per artifact). Add the same events to `events.json`; a failure gets an `id`; its fix is an event with `resolved_by` pointing back, and repeats are one event with `count`.
5. **Stop here unless the PRD itself changes:** the status (one of the four states, waiting for whom), a decision, the plan or the design. Then continue:
6. Update by hand only what is not generated: Status now (focus, four states, three times, waiting lists), Continue here (active slice, branch, PR state as gh reports it, last verified result, next action, blockers, responsible), What it does today (steps and limits that changed), the decision register and anything a new decision invalidates, Acceptance and feedback, the short Log (latest few events + link to the Deník page), What changed (only this version against the previous one).
7. `python3 assets/progress.py render slices.json --page page.html --md draft.md --artifact <id> --events events.json` (also writes `gen:data`).
8. Check, publish (shared steps); refresh the Space homepage if the stage, the four states or the members changed. When a phase completes, write the Retro page and summarise it in the PRD's Retro section.

### Accept (handover to Petr)

1. Create the E2E acceptance plan with `/product-e2e` as a separate artifact with content system `agnes/e2e-test-plan@1` (exit criteria fixed before the run); add it to the Space in group "Převzetí", link it both ways and in the Status links row.
2. After each run: the run summary goes to the Deník page; the "What was verified" table, the feedback register (item, from, when, state, link), known issues, and the verdict (who, when, on which deployment, with which reservations) go to Acceptance as a new PRD version; the accepted state in Status now and on the Space homepage.
3. Write the Retro of the whole build to the Retro page and its main lessons to the PRD.

## Shared steps

### Second opinion (mandatory before every publish that changes the design or a decision, and on every larger update)
- Use the `second-opinion` skill: GPT Astra (`gpt-6-astra`, effort medium) on the full draft, run from the Agnes repo root at fresh `origin/main` so it checks claims against the code. Astra reads only Markdown; give it the English half when the draft is large.
- Ask it for contradictions between parts, statements in the top parts that are stale or unsupported, information lost in collapsed records, and Retro claims without evidence. Incorporate or explicitly rebut every finding; the Second opinion section lists each finding and what was done.

### Build
- Write the Markdown from `assets/template.md` (plus `building-sections.md` once building): both languages in every bilingual section, one marker per section; the slice table, registers and log are English only, outside the language blocks.
- Build the HTML from `assets/template.html` (plus `building-sections.html`): replace all sample content, keep the components and scripts; diagrams as inline SVG styled by design tokens; no external hosts, no storage APIs.
- The page header shows a hardcoded version label (`vN` in the draft's metadata line and in the page header): set it to the version this publish will create (current head + 1).
- Run `python3 assets/check_proposal.py draft.md --page page.html --version vN` (What changed becomes required from v2 on) until both languages report 0 findings and the freshness check reports 0 findings (version label, every PR number linked, generated regions present, next check in the future, every decision card in the register).
- Self-review against the content system checklist: every Agnes claim has a path or link, every competitor claim a source, verified/inferred/unverified labels where needed, no filler, both languages say the same.

### Publish
- New: `agnes artifact create --html page.html --markdown-source draft.md --title "<title>" --visibility instance --audience everyone --design-system ds_C-_CIyerl8dQ1ZzkXFE9zwrn@2 --content-system ef74c6ed49c241f490b6fb95ad65f84e@5 --summary "<1-2 sentences>" --keywords teag-<n>,<topic words>`.
- Update: `agnes artifact update <id> --base-version <head> --require-head --html ... --markdown-source ... --note "<what changed>" --summary ... --keywords ...` (summary and keywords every time). Never drop `--require-head`: without it a stale base publishes anyway and silently replaces whatever another agent published in between. `409 base_not_head` means someone published in between: read the new head, merge, rebuild, retry.
- **Space and Pages** (first publish, or once for an older PRD that has none): check the switches `artifact_knowledge_spaces` and `artifact_space_reader` are on for the instance (a switch line in `agnes admin config export`, then delete the file; if off, publish the PRD alone and tell Petr). Create the homepage with `agnes artifact create --markdown space-home.md --title "<feature> · Prostor" --visibility instance --audience everyone --summary ... --keywords teag-<n>,...`, then `agnes artifact space enable <space>`, `agnes artifact space add <space> <prd> --position 0`, and every existing satellite with `--group-label`; for several members at once prefer the atomic `space curation <space> --json` → edit → `space curate <space> --file`. Reserve the Page ids first so the PRD, homepage and Pages link each other in one pass: `agnes artifact page reserve-ids <prd> --count 2`, then `agnes artifact page create <prd> --title "Deník" --markdown diary.md --page-id ap_...` and the same for "Retro". Check with `agnes artifact space map <space>`.
- Settings: `agnes artifact settings <id> --form-responses` (comments stay visible to everyone; everyone with access may answer).
- Keywords are the public tags: always `teag-<n>` plus 2-5 topic words. Petr's private label: `agnes artifact tag <id> --add <topic>`.
- Link back: the Space and PRD URLs on the Linear issue (`save_issue` with `links`; keep the Linear description short); satellites with `agnes artifact link add` both ways and as Space members.
- Open the published page in Claude in Chrome: no CSP errors, language toggle, grouped TOC, timeline, decision forms, the overdue badge logic, dark mode, phone width; then the Space (homepage, groups, member order) and the Deník and Retro Pages.

### Report to Petr
In Czech, outcome first: the Space and PRD links, version, who can open it, where the feature stands (the four states), what waits for him (one line each), what the independent designers proposed and what was adopted, what Astra changed, what is unverified. Re-read every PR or CI state you mention right before answering. No code in chat.

## Rules
- Facts before claims: verify numbers, paths, states and competitor statements against the source; label anything not verified; missing history is "not recorded", never reconstructed.
- States literally as their tool reports them (OPEN, MERGED, AUTO-MERGE ENABLED) with the time read.
- No AI slop: no filler, hype or generic statements; numbers over adjectives; short sentences.
- One feature, one PRD artifact and one Space: a revision, follow-up research or a status change is a new PRD version, an event is a Deník entry, never a new artifact; satellites only for their own interaction, always as Space members.
- Never publish secrets, customer-specific data or anything with visibility `public`. Server config exports may hold secrets: read only the lines you need and delete the file.
- Do not edit `assets/` during a normal run; improvements to the templates, scripts or systems are a separate, explicit change (republish the content or design system version and update the table above).
